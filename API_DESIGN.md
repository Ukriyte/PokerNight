# PokerNight v2 API Contract

> Audit status: 2026-08-13. This document distinguishes the currently implemented contract from planned pre-frontend work. An endpoint or destination marked **planned** must not be used by a frontend yet.

The API is split by behavior rather than forcing everything through one protocol:

- **REST** handles creation, registration, lobby administration, initial page loading, and refresh recovery.
- **WebSocket/STOMP** delivers live public/private events and accepts time-sensitive game commands.
- The `application` module remains unaware of HTTP, JSON, STOMP, and JWT.

All versioned REST endpoints begin with `/api/v1`.

The production React build is served by the same Spring Boot origin. Frontend code must use relative `/api/v1/...` and `/ws` addresses—never hard-coded localhost or LAN IP values.

## Identity strategy

### Local/LAN milestone

Creating or joining a room returns a random room-scoped bearer token. Clients store it and send:

```http
Authorization: Bearer <token>
```

Tokens identify the subject, room, and role. They are not accepted in a different room.
They expire after seven days by default. Rejection, kicking, and room deletion revoke the affected sessions immediately. REST authorization and STOMP destination authorization consult the same active-session store, so an already-connected socket cannot continue after revocation.

### Production account milestone

| Endpoint | Why it is required | Build now? |
|---|---|---|
| `POST /auth/register` | Create durable name/password account | Later, with PostgreSQL |
| `POST /auth/login` | Verify password and issue access/refresh tokens | Later, with PostgreSQL |
| `POST /auth/refresh` | Renew login without entering password again | Later |
| `POST /auth/logout` | Revoke refresh session | Later |

Passwords must be hashed using Argon2 or BCrypt and never stored in room state. Building these before persistence would create a disposable authentication system, so they do not belong in the first API slice.

## REST endpoints

### Room creation and discovery

#### `POST /api/v1/rooms`

Creates an isolated room and host session.

Request:

```json
{
  "hostName": "Aman",
  "startingChips": 1000,
  "smallBlind": 25,
  "bigBlind": 50,
  "maximumPlayers": 6,
  "botCount": 0,
  "themeId": "midnight",
  "cardPackId": "classic"
}
```

`themeId` and `cardPackId` are room-level presentation settings selected by the host. They are returned inside `config.appearance` by public room, host bootstrap, and player bootstrap responses, so every screen restores the same appearance after refresh or reconnect. Supported themes are `midnight` and `broadcast`; supported card packs are `classic` and `four-color`.

Response `201 Created`:

```json
{
  "roomCode": "A1B2C3",
  "hostToken": "...",
  "hostUrl": "/room/A1B2C3",
  "joinUrl": "/room/A1B2C3/play",
  "tvUrl": "/room/A1B2C3/tv"
}
```

Why: room codes and host identity must be generated by the server. This endpoint is required now.

#### `GET /api/v1/rooms/{roomCode}`

Returns `roomCode`, room configuration, `botPlayerIds`, and public game state. It excludes members, tokens, and hole cards.

Why: host/player/TV pages need a reliable refresh path even if the WebSocket missed events. Required now.

### Joining and approval

#### `POST /api/v1/rooms/{roomCode}/join-requests`

Registers a player as pending and returns a room-scoped player token.

```json
{ "displayName": "Neha" }
```

Why: players need identity before approval and need to recover their pending state after refresh. Required now.

#### `GET /api/v1/rooms/{roomCode}/me`

Authenticated player reconnect lookup. It returns pending/approved/rejected/kicked membership and the public game state. For an approved player it also returns `privateState`, including that player's current hole cards and legal actions. A refreshed phone can therefore rebuild its complete screen before reconnecting STOMP.

`privateState` is `null` while the player is pending, rejected, or kicked.

Why: this is the refresh/reconnect source of truth for player identity and approval. Required before gameplay UI wiring.

#### `GET /api/v1/rooms/{roomCode}/lobby`

Host-only list of pending and approved members.

Why: the host cannot approve users without a lobby projection. Required now.

#### `POST /api/v1/rooms/{roomCode}/members/{playerId}/approval`

Host-only. Body: `{ "seatNumber": 2 }`.

Why: approval and seat assignment must be one atomic operation. Required now.

#### `POST /api/v1/rooms/{roomCode}/members/{playerId}/rejection`

Host-only rejection of a pending player.

Why: explicit rejection provides a stable player status and audit event. Required now.

#### `DELETE /api/v1/rooms/{roomCode}/members/{playerId}`

Host-only kick of an approved player.

Why: the host needs moderation and the engine seat must be released atomically. Required now.

#### `DELETE /api/v1/rooms/{roomCode}`

Host-only room closure.

Why: explicit cleanup is preferable to waiting for stale-room reaping. Required now.

### Game recovery and history

#### `GET /api/v1/rooms/{roomCode}/state`

Returns the current public state. This may be an alias of the public room endpoint initially.

Returns the same public room/game recovery snapshot as the public room endpoint. This stable alias lets the frontend treat state recovery independently from room discovery.

#### `GET /api/v1/rooms/{roomCode}/history?cursor=...`

Returns completed hands and action logs newest first.

Authenticated for either a host or player token. Results are newest first. `limit` defaults to 50 and must be 1–100. Pass the returned `nextCursor` as the next request's exclusive `cursor`; `nextCursor: null` means there are no older entries.

#### `GET /api/v1/rooms/{roomCode}/host-bootstrap`

Host-only recovery response combining the public room snapshot, full lobby snapshot, and first 50 history entries. This is the first request made by a refreshed host page.

## WebSocket/STOMP contract

Connection endpoint: `/ws`

Spring application destinations use `/app`; broker subscriptions use `/topic` and `/user/queue`.

### Client commands

| Destination | Payload | Authorized caller | Why |
|---|---|---|---|
| `/app/rooms/{code}/start-hand` | `{ commandId }` | Host | Begin next hand |
| `/app/rooms/{code}/new-game` | `{ commandId }` | Host | Reset after game completion |
| `/app/rooms/{code}/actions` | `{ commandId, action, amount? }` | Current player | Submit fold/check/call/raise/all-in |

`commandId` is required and client-generated. A successful command is cached by room, authenticated actor, and command ID. Repeating the same ID and payload returns a private receipt with `replayed: true` without executing or broadcasting it again. Reusing an ID with another payload returns `COMMAND_ID_REUSED`.

Command acknowledgements arrive at `/user/queue/commands`:

```json
{ "commandId": "018f...", "replayed": false, "phase": "PRE_FLOP", "handNumber": 4 }
```

Clients keep an unacknowledged command in local storage and resend it after reconnect. They remove it only after receiving this acknowledgement.

The complete client bootstrap and retry order is documented in `RECONNECT_FLOW.md`.

### Public subscriptions

| Destination | Receivers | Content |
|---|---|---|
| `/topic/rooms/{code}/state` | Same-room host and approved players | Full public snapshot |
| `/topic/rooms/{code}/events` | Same-room host and approved players | Discriminated hand/street/action/completion envelopes |
| `/user/queue/lobby` | Host only | Complete lobby snapshot after join/approve/reject/kick |

### Private subscriptions

| Destination | Content |
|---|---|
| `/user/queue/cards` | That player's hole cards |
| `/user/queue/turn` | Valid actions and current betting amounts |
| `/user/queue/status` | Pending/approved/rejected/kicked membership changes and room closure |
| `/user/queue/errors` | Command validation failure |
| `/user/queue/commands` | Command acknowledgement, including whether it was a replay |

Spring user destinations are designed for messages unique to an authenticated session, so private cards should use `/user/queue/...`, never a room topic.

CONNECT frames and every subsequent SEND/SUBSCRIBE frame are authorized. Room topics require a matching room session; player gameplay subscriptions require approved membership; lobby subscriptions require the host role; direct broker-queue subscriptions are denied.

Polymorphic event and status messages use the frozen `{ "type": "...", "payload": { ... } }` envelope defined in `FRONTEND_CONTRACT.md`.

## HTTP status and error format

Errors use RFC 9457-style problem JSON:

```json
{
  "type": "https://pokernight.dev/problems/not-host",
  "title": "Host permission required",
  "status": 403,
  "detail": "Only the room host may perform this operation",
  "code": "NOT_HOST",
  "instance": "/api/v1/rooms/A1B2C3/..."
}
```

Mappings:

- `400`: malformed JSON or invalid configuration
- `401`: missing/invalid token
- `403`: valid token but wrong role or room
- `404`: room not found
- `409`: occupied seat, duplicate member, invalid membership transition, room full
- `422`: valid message shape but illegal poker action

Implemented REST error mappings currently cover validation, authentication, room lookup, authorization, and lobby conflicts. Gameplay errors are currently delivered through `/user/queue/errors`, with codes from `GameplayFailure`. Complete error examples will be frozen in step 10.

## Endpoints we should not build

- A REST endpoint that returns arbitrary players' hole cards.
- A public endpoint containing pending-player details.
- Separate endpoints for `check`, `call`, `raise`, etc.; one action command keeps validation centralized.
- A client endpoint that sets pot, cards, dealer, winner, or current turn. Those are engine-owned state.
- Polling endpoints every few hundred milliseconds. WebSocket events plus REST recovery are simpler and cheaper.

## Implementation sequence

1. Spring Boot module, room REST endpoints, validation, problem responses.
2. **Implemented:** expiring, revocable room-scoped bearer sessions for host/pending player recovery.
3. **Implemented:** gameplay application service that drains engine events.
4. **Implemented:** authenticated STOMP connection and public/private routing.
5. **Implemented:** TTL-bounded command idempotency, optional persisted restart receipts, and private reconnect snapshots.
6. **Implemented:** same-origin SPA delivery with deep-link fallback and immutable hashed assets.
7. **Implemented:** REST and STOMP authorization hardening, cross-room isolation, revocation, and request/frame limits.
8. **Implemented:** memory/file runtime profiles, startup validation, health/info/metrics, correlation IDs, graceful shutdown, and Docker packaging.
9. PostgreSQL accounts/history and JWT access/refresh tokens.
10. Redis room coordination, multi-instance deployment, and CI/CD automation.

The idempotency cache is bounded and defaults to a 24-hour retention window. With JSON persistence enabled, minimal non-private command receipts survive process restart. Expired IDs may be reused. A Redis-backed receipt store is still required before multiple server instances accept commands concurrently.
